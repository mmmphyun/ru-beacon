# Ru-Beacon Decision Log

이 문서는 Ru-Beacon의 설계 논의에서 확정되거나 보류된 결정을 기록한다.
확정되지 않은 내용은 제안 상태로 유지하며, 최종 설계 문서에는 확정된 결정만 반영한다.

## DEC-001: 프로젝트 정체성 및 제품 포지셔닝

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  Ru-Beacon은 Minecraft 서버 운영자가 Discord 커뮤니티를 구축하고 운영하는 데 필요한 기능을 하나의 플랫폼에서 쉽게 설정·관리할 수 있도록 돕는 서버 커뮤니티 운영 플랫폼이다.
- 해결하려는 문제:
  Minecraft 서버 운영자는 여러 Discord 봇을 찾고 설치하며, 채널·방·역할·권한·자동화 기능을 개별적으로 구성해야 한다. Ru-Beacon은 이 과정을 통합한다.
- 제품 포지셔닝:
  Ru-Beacon은 단일 Discord 봇이 아니라 Minecraft 서버용 Discord 커뮤니티 구축·운영 플랫폼이다.

## DEC-002: Core와 Sandbox Modules의 역할 구분

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  - Core는 서버 보안과 운영에 필요한 필수 기능을 제공한다.
  - Sandbox Modules는 필수는 아니지만 여러 서버에서 활용할 수 있는 선택적 확장 기능을 제공한다.
  - Sandbox 실행 엔진은 구현 대상에 포함한다.
  - Sandbox 템플릿은 초기부터 모두 구현하지 않고 실제 수요에 따라 추가한다.

## DEC-003: MVP 규모에 대한 기본 원칙

- 상태: PROPOSED
- 결정일: 2026-08-21
- 제안:
  MVP는 단순 데모가 아니라 실제 운영 가능한 첫 번째 제품 버전으로 정의한다. LLM을 활용하므로 코드 규모 자체를 지나치게 제한하지 않되, 기능별 검증 단위와 운영 시나리오는 작게 나눈다.
- 미확정 사항:
  MVP에 포함할 Core 기능, Sandbox 엔진의 초기 범위, Phase 1에서 제외할 기능은 2단계에서 확정한다.

## DEC-004: 원격 콘솔 범위

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  원격 콘솔은 MVP에 포함하되 축소된 형태로 구현한다. Discord 기반 실행, 허용 명령어 제한, 최고 관리자 권한 검증, 실행 전 확인, 감사 로그를 기본으로 하며 웹 콘솔과 광범위한 명령어 지원은 제외한다.

## DEC-005: 초기 모니터링 범위

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  클라우드 인프라를 도입하기 전 단계에서는 현 단계의 운영에 필요한 최소 모니터링만 구현한다. 서버 상태, TPS/MSPT, 플레이어 수, JVM 메모리, Redis/PostgreSQL 연결 상태, Discord API 오류·지연 및 기본 장애 알림을 우선 대상으로 한다. 전체 관측성 스택은 후속 단계로 둔다.

## DEC-006: Sandbox Module의 제품 개념

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  Sandbox Module은 단순한 사전 제작 템플릿이 아니라, Discord 기능과 Minecraft 이벤트·트리거를 사용자가 자유롭게 조합하고 확장하는 시각적 워크플로우 시스템이다.
- 핵심 동작:
  Minecraft 레벨업 이벤트와 같은 트리거를 Discord 역할 부여, 채널 메시지, 개인 DM 등의 동작에 연결할 수 있다.
- 사용자 경험:
  노드를 선으로 연결하는 그래프 방식 또는 Scratch와 유사한 블록 방식의 편집 경험을 제공할 수 있다.
- Discord 커스터마이징:
  메시지 내용, 버튼 텍스트, 모달 텍스트, 이모지·투표 설정 등 Discord 상호작용에 필요한 사용자-facing 요소를 설정할 수 있어야 한다.
- Minecraft 커스텀 이벤트:
  특정 트리거 명령어를 통해 원하는 시점에 Discord 연동 동작을 발생시킬 수 있어야 한다.

## DEC-007: Sandbox 관련 용어 구분

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 정의:
  - 기본 노드/블록: 사용자가 워크플로우를 구성하는 최소 기능 단위
  - 사용자 워크플로우: 트리거·조건·동작을 연결해 만든 자동화 흐름
  - 템플릿: 자주 쓰이는 사용자 워크플로우를 미리 구성해 둔 예시 또는 설치 단위
  - 확장 모듈: 새로운 트리거·조건·동작·Discord 상호작용을 추가하는 확장 단위
- 정정:
  기존 논의에서 사용한 “모듈 내부에 미리 정의된 기능”이라는 표현은 모호하므로 사용하지 않는다. 필요한 경우 기본 노드 또는 템플릿이라는 용어를 사용한다.

## DEC-008: Sandbox 워크플로우의 양방향성

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  Sandbox 워크플로우는 Minecraft 이벤트가 Discord 동작을 발생시키는 방향뿐 아니라, Discord 상호작용이 Minecraft 서버에 영향을 주는 방향도 동일하게 지원한다.
- 예시:
  - Minecraft 레벨업 → Discord 역할 부여·채널 메시지·개인 DM
  - Discord 버튼 승인 → Minecraft 명령 실행 또는 플레이어 상태 변경
  - Discord 모달 제출 → Minecraft 플레이어 정보 처리

## DEC-009: MVP 기본 노드 선정 원칙

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  MVP에서는 모든 Discord·Minecraft 기능을 노드화하지 않는다. 초기 템플릿 또는 대표적인 양방향 수직 슬라이스를 먼저 정하고, 그 흐름을 테스트할 수 있는 기본 노드만 구현한다.
- 원칙:
  기본 노드는 단위 테스트·통합 테스트·E2E 테스트가 가능한 동작부터 선정한다.

## DEC-010: 기능 중심 웹 대시보드

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  웹 대시보드는 MVP 또는 Phase 1에 포함한다. 초기에는 시각적 완성도보다 워크플로우 생성·편집·저장·활성화·실행 확인 등 기능 구현을 우선한다.
- 범위:
  디자인 시스템과 고급 UX는 후속 개선 대상으로 두되, 사용자가 모듈과 노드를 연결할 수 있는 기능적 화면은 초기부터 제공한다.

## DEC-011: 외부 개발자 확장 모듈의 의미

- 상태: DEFERRED
- 결정일: 2026-08-21
- 정의:
  외부 개발자 확장 모듈은 새로운 Minecraft 커스텀 이벤트만을 의미하지 않는다. 새로운 트리거, 조건, 액션, Discord 상호작용, 외부 서비스 연동을 Ru-Beacon에 추가하는 확장 단위를 의미한다.
- 포함될 수 있는 예:
  - 외부 플러그인이 발행하는 Minecraft 이벤트 어댑터
  - 새로운 Discord 액션 노드
  - 외부 API 연동 노드
  - 새로운 데이터 변환·조건 노드
- 결정:
  외부 개발자용 SDK·플러그인 시스템은 MVP에서 구현하지 않는다. 다만 초기 노드 구조는 향후 확장을 막지 않도록 설계한다.

## DEC-012: MVP 대표 Sandbox 템플릿

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  MVP는 양방향 워크플로우를 검증하기 위해 대표 템플릿 2개를 포함한다.
- 템플릿 A: Minecraft 시작형 보상 수령
  - Minecraft 레벨업 또는 업적 달성
  - Discord 채널 메시지와 보상 수령 버튼 표시
  - 버튼 클릭 사용자와 Minecraft 계정 연동 확인
  - Minecraft 명령 실행 또는 보상 지급
  - Discord 개인 DM으로 결과 안내
- 템플릿 B: Discord 시작형 일일 출석 보상
  - 매일 오전 9시에 보상 횟수 초기화
  - Discord 출석 버튼 클릭
  - Minecraft 서버 내 플레이어 존재 여부 확인
  - 해당 날짜의 보상 잔여 수량 확인
  - 선착순 100명 제한 적용
  - 중복 출석 방지 후 Minecraft 보상 지급
  - Discord 결과 안내
- 목적:
  두 템플릿을 통해 Minecraft→Discord와 Discord→Minecraft 양방향 흐름, 예약 초기화, 동시성 제어, 멱등성, 사용자 검증, 보상 수량 제한을 검증한다.

- 결정:

## DEC-015: 운영 시간대 설정

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  일일 초기화 시간은 서버 호스팅 위치나 Discord 국가 추정으로 결정하지 않는다. Ru-Beacon 설치 단위가 IANA 시간대(예: `Asia/Seoul`)를 직접 설정하며, 초기 기본값은 `Asia/Seoul`로 둔다.
- 이유:
  게임 서버 호스팅 위치는 운영 커뮤니티의 기준 국가와 다를 수 있고, Discord 서버에는 신뢰할 수 있는 국가 정보가 없으며, IP 기반 자동 추정은 VPN·모바일 네트워크·개인정보 문제를 가진다.
- UX:
  웹 대시보드에서 시간대를 선택·변경할 수 있게 한다. 브라우저 지역 설정은 자동 확정이 아니라 초기 추천값으로만 활용할 수 있다.

## DEC-016: 출석 보상 수량 범위

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  보상 수량과 일일 제한은 게임 서버와 Discord 커뮤니티가 연결된 운영 단위(설치·테넌트)별로 관리한다.
- 설명:
  현재 기본 운영 모델은 하나의 게임 서버와 하나의 Discord 커뮤니티를 연결하는 것이다. 다만 향후 여러 커뮤니티 또는 여러 서버를 지원할 수 있도록 quota scope를 운영 단위에 귀속한다.
- 예시:
  운영 단위 A의 일일 보상 100개와 운영 단위 B의 일일 보상 100개는 서로 영향을 주지 않는다.

## DEC-017: 출석 보상 지급·복구 처리

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  보상 수량 차감과 지급 결과는 동시성 제어와 멱등성 처리를 포함해야 한다. 지급 실패 시 예약된 보상 수량을 복구한다.
- 기본 흐름:
  1. 운영 단위·날짜·사용자 기준 중복 출석 여부 확인
  2. 남은 수량을 원자적으로 예약
  3. Minecraft 보상 지급 요청
  4. 성공 시 출석 완료 확정
  5. 실패·타임아웃 시 예약 수량 복구
- 중복 방지 키:
  운영 단위 + 보상일 + Minecraft 계정 식별자를 사용한다.

## DEC-018: 출석 상호작용 결과 안내

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  버튼 클릭 결과는 Discord Ephemeral Message를 우선 사용해 요청자에게만 표시한다. 메시지 내용은 워크플로우 설정에서 커스터마이즈할 수 있어야 한다.
- 안내 대상:
  성공, 이미 출석 완료, 오프라인, 계정 미연동, 보상 소진, 지급 실패를 각각 구분한다.

## DEC-019: MVP Core 및 대표 이벤트 범위

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  MVP에는 기존에 정의한 Core 기능 전체를 포함한다. Minecraft 시작형 템플릿은 레벨업 이벤트, 업적 달성 이벤트, 특정 트리거 명령어를 모두 지원한다.

- 명령어 변수:
  `{User_Nickname}`과 같은 컨텍스트 변수를 명령어에 주입할 수 있어야 한다.

## DEC-020: Sandbox 자유도 및 보상 커스터마이징

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  Sandbox는 특정 템플릿의 고정 동작을 제공하는 기능이 아니라 사용자가 원하는 흐름을 조합할 수 있는 것을 최우선 가치로 둔다.
- 출석 보상 설정:
  - 보상 수량은 관리자가 설정한다.
  - 100개는 기본 예시값일 뿐 고정값이 아니다.
  - 동일한 보상, 랜덤박스, Discord 역할별 차등 보상을 지원할 수 있어야 한다.

- 상태: CONFIRMED

## DEC-029: 2FA 장애 및 비상 복구 제안

- 원칙:

## DEC-046: 표준 이벤트 봉투

- 상태: CONFIRMED
- 결정일: 2026-08-21
- 결정:
  모든 표준 이벤트는 공통 이벤트 봉투를 사용한다. 이벤트별 데이터는 `payload`에 넣고, 봉투 필드는 전달·추적·중복 방지·버전 관리를 담당한다.
- 필수 봉투 필드:
  - `event_id`: producer가 발급하는 전역 고유 이벤트 식별자
  - `event_type`: 표준 이벤트 타입
  - `source`: `minecraft`, `discord`, `system`, `external` 등 발생 계층
  - `source_instance_id`: 이벤트를 발생시킨 게임 서버·Discord 설치·서비스 인스턴스 식별자
  - `tenant_id`: 이벤트가 속한 Ru-Beacon 운영 단위
  - `occurred_at`: 원천에서 이벤트가 발생한 시각
  - `received_at`: Ru-Beacon이 이벤트를 수신한 시각
  - `correlation_id`: 하나의 사용자 동작·워크플로우 실행을 추적하는 식별자
  - `causation_id`: 현재 이벤트를 발생시킨 상위 이벤트 또는 노드 실행 식별자
  - `idempotency_key`: 부작용이 있는 처리의 중복 실행을 방지하는 키
  - `actor`: 이벤트를 유발한 주체. 없을 수 있음
  - `subject`: 이벤트의 대상. 없을 수 있음
  - `schema_version`: 이벤트 봉투와 payload 스키마 버전
  - `payload`: 이벤트 타입별 데이터
- 원칙:
  필드의 의미와 타입은 안정적으로 유지하고, 새로운 데이터는 `payload`와 버전 규칙으로 확장한다. 필드 제거·의미 변경은 새 schema version으로 처리한다.

## DEC-050: 운영 단위와 Minecraft 서버 네트워크

  ```text
  Ru-Beacon Service

      └── Minecraft Network B

  ├── Discord Community A
  └── Minecraft Network A
      ├── Proxy
      ├── Backend Server A
      └── Backend Server B
  ```

- 기본 동작:

## DEC-077: PING 하트비트 RDB 부하 격리 및 하이브리드 Presence 정합성 (결함 8, 10)

- 상태: CONFIRMED
- 결정일: 2026-09-15
- 결정:
  1. **PING 하트비트 Redis TTL 격리 (결함 8 해결)**:
     - 30초 주기 WSS PING 프레임 수신 시마다 수행하던 PostgreSQL 동기 UPDATE를 전면 배제하고 Redis `SETEX presence:instance:{id} 60 {timestamp}`로 전환한다.
     - RDB 동기화는 세션 최초 핸드셰이크(ONLINE) 및 정상 종료(OFFLINE) 시에만 수행하여 DB 커넥션 풀 고갈 및 WAL 쓰기 부하를 99.9% 차단한다.
  2. **하이브리드 인스턴스 생존 상태 정합성 모델**:
     - 단건 상세 조회: Redis Read-Through(`presence:instance:{id}` 존재 확인)를 통해 0초 지연의 실시간 온라인 상태를 동적 판정한다.
     - 목록/인덱스 정합성: 비정상 크래시 세션으로 인한 RDB `WHERE status = 'ONLINE'` 인덱스 왜곡을 방어하기 위해, 백엔드 내부의 60초 주기 초경량 코루틴 리퍼(`reapStaleInstances`)가 Redis 키가 없는 인스턴스를 단일 UPDATE 쿼리로 `STALE`로 일괄 전이한다 (CPU 0.001% 미만, 실행 시간 2~5ms).
  3. **웹소켓 256KB 보안 가드 및 클레임 체크(Claim Check) 설계 원칙**:
     - Ktor WebSockets에 `maxFrameSize = 256KB`를 설정하여 텍스트성 마인크래프트 이벤트는 안전하게 수용하면서 비인가 거대 페이로드에 의한 OOM DoS를 차단한다.
     - 수만 개 블록 데이터나 월드 롤백 스냅샷 등 대용량 데이터는 WSS JSON 청크 분할(복잡도/메모리 누수 위험)을 금지하고, S3/R2 오브젝트 스토리지에 직접 업로드 후 WSS로는 1KB 미만의 파일 Key/요약 메타데이터만 전송하는 클레임 체크 패턴을 강제한다.
  4. **K8s API Service 파드 확장 정합성 (결함 10 해결)**:
     - Redis Pub/Sub 분산 세션 라우팅을 기반으로 Helm `apiService.replicaCount`를 2로 기본 상향하며, 향후 수십 대 규모로 확장 시 `instanceId -> Pod IP` 분산 맵으로 전환하는 단계적 로드맵을 수립한다.
