## 1. Ru-Beacon의 정체성

Ru-Beacon은 Minecraft 커뮤니티의 Discord 운영을 하나의 플랫폼에서 구성하고 자동화하는 서비스다. Discord의 역할·채널·버튼·모달·메시지·투표와 Minecraft의 표준 이벤트 및 서버 명령어를 시각적 Sandbox 워크플로우로 연결한다.

핵심 가치는 특정 기능을 고정해 제공하는 것이 아니라 운영자가 원하는 동작을 안전하게 조합하고 커스터마이즈할 수 있게 하는 데 있다.

기본 운영 단위는 하나의 Discord 커뮤니티와 하나의 Minecraft 네트워크의 결합이다. 네트워크는 프록시 인스턴스와 여러 백엔드 서버 인스턴스로 구성될 수 있다.

## 2. 과거 문제

초기 프로젝트는 서버 운영 중 반복되는 불편을 해결하려는 목적에서 시작했지만, 기능·서비스·문서의 경계가 충분히 정리되지 않은 상태에서 확장되었다.

주요 문제는 다음과 같다.

- Discord와 Minecraft의 설정 및 운영 작업이 분산되어 반복 입력이 많았다.
- 계정 연결, 권한, 명령어, 이벤트 연동이 하나의 일관된 운영 모델로 묶이지 않았다.
- 자동화 기능을 늘릴수록 사용자가 내부 구현과 변수 처리 방식을 이해해야 했다.
- API, 데이터 저장소, Minecraft 모듈의 책임이 겹치면 장애와 부하의 영향 범위를 통제하기 어려웠다.
- 인증·원격 명령·보상 지급처럼 실패 시 영향이 큰 기능의 중복 실행과 복구 정책이 명확하지 않았다.
- 클라우드 운영 역량과 포트폴리오 증거를 어떤 방식으로 남길지 초기 설계에 포함되지 않았다.

## 3. 문제의 원인

### 3.1 제품 경계보다 기능 목록이 먼저 늘어남

Discord 기능, Minecraft 이벤트, 템플릿, 외부 확장 기능이 같은 수준에서 논의되면서 코어 기능과 선택 기능을 구분하기 어려웠다. 결과적으로 MVP의 성공 조건과 제외 범위가 흔들릴 위험이 있었다.

### 3.2 실행 모델과 데이터 소유권이 분리되지 않음

워크플로우 실행을 API 요청 처리와 같은 책임으로 두거나 Minecraft 모듈이 데이터베이스에 직접 접근하면, 부하·권한·장애 전파를 서비스 경계 밖에서 통제하게 된다.

### 3.3 분산 이벤트의 의미가 명확하지 않음

이벤트의 식별자, 중복 방지, 전달 보장, 장애 중 유실 여부, 재시도 정책이 계약으로 고정되지 않으면 같은 이벤트가 여러 번 처리되거나 오래된 이벤트가 복구 후 실행될 수 있다.

### 3.4 운영 실패를 제품 요구사항으로 다루지 않음

Discord·Redis·PostgreSQL·Minecraft 모듈 중 하나가 장애 났을 때 무엇을 계속 허용하고 무엇을 거부할지, 관리자에게 언제 어떻게 알릴지 정하지 않으면 서비스 장애가 곧 사용자 서버의 운영 장애가 된다.

### 3.5 확장성을 복잡성으로 오해할 위험

자유도를 높이기 위해 모든 기능을 처음부터 구현하면 Scratch 수준의 사용성을 잃을 수 있다. 따라서 자유도는 노드·변수·조건·병렬 블록의 일관된 모델로 제공하고, 기능 수 자체는 표준 이벤트와 안전한 동작부터 단계적으로 늘려야 한다.

## 4. 재설계 목표

1. 운영자가 Discord 커뮤니티와 Minecraft 네트워크를 한 곳에서 설정한다.
2. 계정 연결·권한·2FA·원격 명령을 보수적인 기본값과 명시적인 동의 아래 제공한다.
3. Discord 시작 이벤트와 Minecraft 시작 이벤트를 동일한 Sandbox 모델로 조합한다.
4. API는 요청·설정·조회에 집중하고 Workflow Worker가 워크플로우 실행을 담당한다.
5. Minecraft 모듈은 데이터베이스에 직접 접근하지 않고 통제된 이벤트·명령 경로만 사용한다.
6. 중복 실행, 부분 실패, 이벤트 유실, 장애 복구의 정책을 문서와 계약으로 검증 가능하게 한다.
7. 공개 베타에서 실제 운영 데이터를 수집하되, 개인정보와 타 서버의 운영 리스크를 최소화한다.
8. 네트워크·컨테이너·CI/CD·관측성·SLO·장애 대응을 포트폴리오 증거로 남긴다.

## 5. 포트폴리오 관점

Ru-Beacon은 보안 기능만 보여주는 프로젝트가 아니라, 보안 요구를 가진 분산 클라우드 서비스를 설계·배포·운영하는 프로젝트로 포지셔닝한다. 부트캠프의 보안 자동화 주제와 중복되는 인증·접근통제는 제품의 안전장치로 사용하고, 서비스 분리·이벤트 처리·관측성·신뢰성·비용과 운영 개선을 클라우드 역량의 핵심 증거로 삼는다.

구체적인 실험과 증거 형식은 [PORTFOLIO_EVIDENCE_PLAN.md](PORTFOLIO_EVIDENCE_PLAN.md)에서 관리한다.
